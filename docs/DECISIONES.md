# Decisiones técnicas

| # | Decisión | Motivo |
|---|---|---|
| D1 | Base de datos **Supabase (PostgreSQL)** y despliegue en **Vercel** | Petición del usuario. |
| D2 | TypeScript en todo el proyecto: React + Vite para la interfaz y funciones de Vercel para la API | Un solo lenguaje. El motor de cálculo se comparte entre servidor e interfaz. |
| D3 | Una sola función `api/index.ts` y un router propio (`src/server/router.ts`) basado en `Request → Response` | El mismo código sirve en Vercel y en local (`scripts/dev-server.ts`). Las reescrituras de `vercel.json` envían `/api/*` a la función. |
| D4 | Conexión con `postgres.js` mediante el **pooler de transacciones** de Supabase (`prepare: false`) | Recomendado para funciones serverless; evita agotar conexiones. |
| D5 | **RLS activado sin políticas** en todas las tablas | La clave anónima de Supabase no puede leer ni escribir nada. Solo el servidor, con la conexión directa, accede a los datos. |
| D6 | **PGlite** (PostgreSQL embebido) para pruebas y desarrollo sin Supabase | Docker no estaba disponible. Ejecuta el mismo SQL de `supabase/migrations`. |
| D7 | Aritmética **racional exacta con BigInt** (`src/engine/rational.ts`) | Requisito de precisión: no hay redondeos silenciosos y el precio mínimo publicable se calcula con techo al cobre. |
| D8 | Precio desconocido = `null` en todo el sistema; `minBuyout`/`marketValue` = 0 de TSM → `null` | Requisito: un precio desconocido nunca equivale a cero. |
| D9 | Identidad del objeto = `itemId`; nunca el nombre | Puede haber objetos distintos con el mismo nombre. |
| D10 | La vendibilidad se deduce de la vinculación (Blizzard) **o** de la observación en datos de subasta de TSM; si no hay ninguna de las dos, es «desconocida» | Evita clasificar como vendible algo sin evidencia. |
| D11 | Resultado con otro objeto del mismo nombre → bloqueo salvo que el usuario asuma la variante manualmente | No se puede saber cuál se obtiene. |
| D12 | Sin expansiones: todo el catálogo es «WoW Forever» | Forever tiene un único rango por profesión. |
| D13 | El catálogo de Blizzard se sincroniza con un **script local** (`npm run sync:catalog`), no desde Vercel | Son miles de peticiones y superan el límite de tiempo de una función. Es reanudable. |
| D14 | Precios: sincronización bajo demanda (botón, sin repetir en menos de 50 min la casa y 6 h la región) más **Vercel Cron diario** y GitHub Actions cada hora (D24) | El plan Hobby de Vercel solo permite cron diario. Con Pro se puede cambiar a cada 3 h en `vercel.json`. |
| D15 | Se conservan como máximo 2 lotes con filas por archivo y contexto; los intentos fallidos se registran sin filas | Mantiene la base de datos dentro del plan gratuito de Supabase y permite reproducir resultados recientes. |
| D16 | Sin modo demo en la aplicación. Los datos ficticios solo existen en las pruebas automáticas (`tests/helpers/seed.ts`, PGlite en memoria) | El usuario pidió que solo exista WoW Forever. |
| D17 | Acceso con una contraseña compartida (`APP_PASSWORD`) | Aplicación de un solo usuario; ver `src/server/auth.ts`. |
| D18 | Las importaciones relativas usan la extensión `.js` | Vercel compila cada archivo TS por separado; Node resuelve `.js` en tiempo de ejecución. Se verificó compilando con `tsc` y ejecutando la función con Node. |
| D19 | **Solo World of Warcraft: Forever** (decisión del usuario, 12-11-2026) | Se retiraron del código y de Supabase Retail, Classic y el modo demo. Forever no tiene reinos ni commodities: se usan las casas de subastas de TSM por modo de juego y facción. |
| D20 | Parámetros jsonb con `$n::text::jsonb` | Con postgres.js un `JSON.stringify` en una columna jsonb se guardaba como cadena (doble codificación). La migración `20261112000000` corrige las filas existentes. |
| D21 | Precios de la casa de subastas desde la **API de Blizzard**; TSM como respaldo y para la demanda regional | Blizzard publica las 15 casas de Forever, incluida la neutral de Aguasnegras, que TSM no tiene. Su foto se resume por objeto en el formato CSV de TSM para reutilizar la ingesta. El modo de cada grupo de casas se verificó contra TSM (`docs/VALIDACION_FUENTES.md`). |
| D22 | Comisión de Aguasnegras separada (`commissionNeutral`, 15 %) | Las casas neutrales cobran más en Classic. Supuesto configurable, no verificado en Forever. |
| D23 | Historial propio en `price_history` (un registro por objeto y día); `historical` = media de los promedios diarios de 14 días | Blizzard solo da la foto actual y TSM no publica Aguasnegras. Una misma foto (mismo `Last-Modified`) cuenta una sola vez. |
| D24 | Sincronización horaria con GitHub Actions además del cron diario de Vercel | El plan Hobby solo permite cron diario. El cron solo sigue la casa del usuario (`pvp-horde`) para no pasar de los 60 s de la función. |
| D25 | Interfaz con el estilo del juego (paneles oscuros tipo tooltip, dorado, colores de calidad, monedas; reglas de la skill UI UX Pro Max). Sustituyó al tema claro de la primera iteración e iconos de WoW por id desde Wowhead (`dataEnv=16`) con respaldo de Blizzard, guardados en `visual_asset` | Los iconos se asocian por id verificado, nunca por nombre; se resuelven con un script local para no depender de Wowhead en cada visita. Detalle en `docs/SISTEMA_VISUAL.md`. |
| D26 | Límite de 30 s para lecturas fuera de transacción; si se supera, se descarta el pool de conexiones | Con el pooler de transacciones se observaron consultas que nunca terminaban (servidor en `ClientRead`) y dejaban la API sin responder. Las ingestas en transacción no se limitan. Ajustable con `DATABASE_QUERY_TIMEOUT_MS`. |
| D28 | **Precio de venta atípico** (`checkSellPrice` en `src/server/evaluate.ts`): si el precio de la casa supera 3 veces el valor regional de TSM, o no hay valor regional y el ROI estimado pasa del 1000 %, la receta queda en «Datos insuficientes» con el motivo y se ordena detrás de las confirmadas | Una sola publicación cara fijaba el valor de mercado (p. ej. Calamar a la parrilla a 453 o, ROI ≈ 836 812 %). No se guarda el número de publicaciones por objeto, así que se compara con la referencia regional. No se cambia el precio ni se oculta: se muestra con la etiqueta «Precio atípico» o «Sin confirmar». Un precio de venta manual no se comprueba. Con los datos del 13-11-2026 afecta a 23 de 2 493 recetas. |
| D27 | **Subida de nivel** (`#/nivel`) con recetas y umbrales de Wowhead guardados en el repositorio (`data/leveling/forever-wowhead.json`) y precios de la casa de subastas elegida (campo de compra de «Ajustes») | Blizzard no publica umbrales de dificultad ni nivel de aprendizaje. Wowhead bloquea las descargas automáticas (HTTP 202), así que los datos se copiaron desde un navegador y se actualizan a mano. Para cada punto se elige la receta con menor costo esperado por punto (costo ÷ probabilidad × puntos). Probabilidad: naranja 1; amarillo y verde (gris − nivel) / (gris − amarillo), estimación de la comunidad. Por defecto solo recetas de instructor e iniciales (deducidas); el usuario puede incluir las de patrón, botín o misión. Objetivo por defecto 300 (Artesano en Classic). Un material sin precio deja el tramo «sin datos» (nunca 0); el usuario puede dar un precio manual, que se guarda solo en su navegador. |
| D29 | **Recetas con tiempo de reutilización fuera de la subida de nivel** (`data/leveling/forever-cooldowns.json`) | La ruta de Alquimia usaba «Transmutar: hierro a oro» (barras de hierro y oro, parecía de Herrería), que tiene 1 h de reutilización y no se puede repetir. Se comprobó el tooltip de Wowhead de las 2 215 recetas (13-11-2026): 15 tienen reutilización (todas las transmutaciones, Tela lunar y Fogata básica) y nunca se eligen. Una transmutación nueva sin comprobar se trata como con reutilización. |
| D31 | **Reutilización en el comparador, el detalle y el plan** (PB-22; `src/server/cooldowns.ts`, `src/engine/cooldown.ts`) | El comparador ponía «Transmutar: arcanita» entre las más rentables sin decir que solo se puede fabricar una vez cada 47 h. Los tiempos de D29 son por hechizo de Wowhead y el catálogo usa ids de receta de Blizzard: se enlazan por objeto creado + materiales obligatorios exactos (14 recetas del catálogo con reutilización). La ganancia y el estado no cambian (son por fabricación); se muestra la etiqueta «1 cada X», una nota en el detalle y un aviso en el plan con el tiempo mínimo ((N − 1) × reutilización). Sin coincidencia en Wowhead la reutilización es desconocida (`null`), nunca 0. |
| D30 | **Servidor MCP local de solo lectura** (`src/mcp/server.ts`, stdio, registrado en `.mcp.json`) | Petición del usuario: consultar los datos desde Claude. Llama a `handle()` dentro del proceso solo con GET, así reutiliza la validación y la lógica de la API sin duplicarla y no puede escribir ni sincronizar. Corre en el equipo del usuario con su `.env`; no se publica en Vercel (sería otra puerta de entrada a los datos). Devuelve oro con 4 decimales (truncado, solo para mostrar) y `null` para lo desconocido. |
| D32 | **Conexión con Battle.net** (`src/server/battlenet.ts`):<br>• OAuth con código de autorización, ámbito `openid wow.profile`.<br>• `state` aleatorio de un solo uso (10 min), guardado como SHA-256 y ligado a una cookie del navegador que empezó.<br>• Intercambio del código en el servidor.<br>• Token cifrado con AES-256-GCM (clave HKDF de `BNET_TOKEN_KEY` o del secreto del cliente) y nunca enviado al navegador.<br>• Cookie de sesión con un id aleatorio (en la base, su SHA-256), `HttpOnly`, `SameSite=Lax` y `Secure`.<br>• Propietario = `sub` de Battle.net. | Lax porque la vuelta desde oauth.battle.net es una navegación de otro sitio y una cookie Strict no llegaría. No hay token de renovación: al caducar (`expires_in`), hay que volver a conectar. No se usa PKCE: Blizzard no lo documenta y el cliente es confidencial (secreto solo en el servidor).<br>Solo la vuelta (`/api/auth/battlenet/callback`) es pública. Sin un `state` válido no hace nada. El resto sigue detrás de `APP_PASSWORD`.<br>Toda ruta de `/api/me/*`:<br>• filtra por la cuenta de la sesión (404 igual exista o no en otra cuenta);<br>• si cambia datos, rechaza un `Origin` ajeno.<br>Desconectar borra las sesiones, y opcionalmente todos los datos de la cuenta (en cascada). |
| D33 | **Datos del personaje con procedencia** (`profession_snapshot`, `profession_manual`, `character_sync`) | Las Profile APIs de Classic no documentan profesiones y Forever no está documentado (PC-01). Por eso:<br>• El namespace se configura (`BNET_PROFILE_NAMESPACES`) y cada intento guarda su código HTTP.<br>• Si la API no da el dato, se guarda «no disponible» y el usuario lo escribe a mano.<br>• El dato manual no sobrescribe el oficial. Se usa el manual salvo que el usuario prefiera el de Blizzard. Un nivel desconocido es `null`, nunca 0.<br>• Al registrar progreso, un dato de Blizzard menor que el último observado se rechaza como posible foto atrasada (409) hasta que el usuario lo confirme a mano. |
| D34 | **Ruta más rápida** (`src/engine/route.ts`) | «Rápida» = menor tiempo activo esperado: fabricaciones esperadas × tiempo de lanzamiento de Wowhead. Con presupuesto:<br>• relajación lagrangiana (tiempo + λ·costo, bisección sobre λ);<br>• mejora voraz por segundos ahorrados por cobre;<br>• se presenta como «la más rápida entre las evaluadas». En la prueba exhaustiva pequeña coincide con el óptimo, pero no se garantiza en general.<br>La «barata» sigue siendo D27. La probabilidad en amarillo y verde es la estimación de la comunidad, o «solo naranja» si el usuario lo pide; cada paso separa lo esperado del mínimo garantizado.<br>No se inventan tiempos de viaje, compra ni aprendizaje («no incluido»). Los rangos del instructor son reglas de Classic sin verificar. La venta de lo fabricado es una recuperación hipotética que no se resta del costo. |
